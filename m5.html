Learning Objective (ILO)

Implement basic DNS services and understand the complete name resolution process to enable users to access network resources using human-readable domain names instead of IP addresses.

What is DNS?

The Domain Name System (DNS) is a hierarchical distributed naming system that translates human-readable domain names (like www.example.com) into IP addresses (like 192.0.2.1). Without DNS, users would need to memorize IP addresses for every website they want to visit!

Key Point: DNS is essential infrastructure that makes the internet user-friendly by allowing access via memorable names instead of numeric IP addresses.

Why DNS Matters

  • ✅ Human-readable naming
  • ✅ Load balancing across servers
  • ✅ Redundancy and failover
  • ✅ Email routing (MX records)
  • ✅ Service discovery

DNS Hierarchy

Root (.) → TLD (.com)
↓
Domain (example.com)
↓
Subdomain (www.example.com)

DNS Components & Records

DNS Server Types

Authoritative: Maintains actual DNS records for a domain

Recursive: Queries other servers on behalf of clients

Caching: Stores frequently accessed DNS records

Common DNS Record Types

A Maps domain name to IPv4 address
AAAA Maps domain name to IPv6 address
CNAME Canonical name - alias for another record
MX Mail exchange - routes emails
NS Name server - delegates domain authority
SOA Start of authority - zone information
PTR Pointer - reverse DNS lookups
TXT Text records - SPF, DKIM, verification

DNS Caching & TTL

TTL (Time To Live): Specifies how long DNS records are cached (in seconds). Higher TTL = faster lookups but slower updates. Lower TTL = slower lookups but faster changes.

Example: TTL 3600 = records cached for 1 hour

DNS Name Resolution Process

When a user types a URL, here's what happens behind the scenes:

1

User Query

User types URL (e.g., www.example.com) in browser

User → Browser: Resolve www.example.com
2

Recursive Resolver Query

Browser queries recursive resolver (usually ISP's DNS or 8.8.8.8)

Browser → Resolver: What's the IP for www.example.com?
3

Root Nameserver Query

Resolver queries root nameserver for domain information

Resolver → Root: Where is .com authority?
4

TLD Nameserver Query

Resolver queries TLD nameserver for authoritative nameserver

Resolver → TLD: Where is example.com authority?
5

Authoritative Nameserver Query

Resolver queries authoritative nameserver for actual record

Resolver → Auth NS: What's the A record for www.example.com?
6

Response Back to User

IP address returned through chain back to browser

Resolver → Browser → User: 192.0.2.1 ✓

Quick DNS Resolution Summary

User Query: www.example.com
↓ Recursive Resolver (ISP DNS)
↓ Root Nameserver (".") - Refers to .com TLD
↓ TLD Nameserver (".com") - Refers to example.com NS
↓ Authoritative Nameserver - Returns: 192.0.2.1
↓ Response cached & returned to user
✓ Browser can now connect to 192.0.2.1

🔧 Complete DNS Configuration Example

Let's configure a DNS server for a company network with multiple subdomains.

1

Plan Your DNS Infrastructure

Domain: company.local (internal network)

DNS Server IP: 192.168.1.10

Subdomains to configure:

  • • www.company.local → 192.168.1.50 (Web Server)
  • • mail.company.local → 192.168.1.60 (Mail Server)
  • • admin.company.local → 192.168.1.70 (Admin Server)
  • • ftp.company.local → 192.168.1.80 (FTP Server)
2

Configure DNS Zone File

Create zone file for company.local domain:

$TTL 86400 @ IN SOA ns1.company.local. admin.company.local. ( 2024010101 ; Serial 3600 ; Refresh 1800 ; Retry 604800 ; Expire 86400 ; Minimum TTL ) @ IN NS ns1.company.local. ns1 IN A 192.168.1.10 company IN A 192.168.1.10 ; A Records www IN A 192.168.1.50 mail IN A 192.168.1.60 admin IN A 192.168.1.70 ftp IN A 192.168.1.80 ; CNAME Records (Aliases) webserver IN CNAME www.company.local. mail-srv IN CNAME mail.company.local. ; MX Record (Mail Server) @ IN MX 10 mail.company.local. ; TXT Record (Verification) @ IN TXT "v=spf1 mx ~all"
3

Configure DNS Server (BIND/named)

Edit /etc/bind/named.conf to add zone:

zone "company.local" { type master; file "/etc/bind/zones/db.company.local"; allow-transfer { 192.168.1.11; }; }; zone "1.168.192.in-addr.arpa" { type master; file "/etc/bind/zones/db.1.168.192"; }; // Allow recursive queries from internal network acl "internal" { 192.168.1.0/24; 127.0.0.1; }; options { directory "/var/cache/bind"; recursion yes; allow-recursion { internal; }; dnssec-validation auto; listen-on { 192.168.1.10; 127.0.0.1; }; };
4

Configure Router to Use DNS

Cisco Router configuration (DHCP + DNS):

! Enable DNS services ip dns server ip dns name-list 1 permit company.local ip dns primary-server 192.168.1.10 ! Configure DHCP pool with DNS ip dhcp pool CORP_NETWORK network 192.168.1.0 255.255.255.0 default-router 192.168.1.1 dns-server 192.168.1.10 domain-name company.local lease 7 ! Configure DHCP relay if needed interface Fa0/1 ip helper-address 192.168.1.10 ! Verify DNS configuration show ip dns show ip dns view
5

Test DNS Resolution

Verify DNS is working from client:

! Test DNS resolution on client C:\> nslookup www.company.local Server: 192.168.1.10 Address: 192.168.1.10#53 Name: www.company.local Address: 192.168.1.50 ! Test reverse DNS lookup C:\> nslookup 192.168.1.50 Server: 192.168.1.10 Address: 192.168.1.10#53 50.1.168.192.in-addr.arpa name = www.company.local ! Dig command (Linux/Mac) $ dig www.company.local @192.168.1.10 $ dig mail.company.local @192.168.1.10 $ dig +short company.local MX $ dig -x 192.168.1.50 @192.168.1.10 ! Ping using DNS name C:\> ping www.company.local Pinging www.company.local [192.168.1.50] with 32 bytes... Reply from 192.168.1.50: bytes=32 time=1ms TTL=128 ! Verify DHCP provides DNS ipconfig /all (Should show DNS Servers: 192.168.1.10)
6

Configure DNS Caching & Forwarding

Optimize DNS performance:

! Configure forwarders for external domains ip dns server ip dns forwarding ip name-server 8.8.8.8 ip name-server 8.8.4.4 ! Set DNS cache timeout ip dns cache timeout 300 ! Monitor DNS cache show ip dns cache show ip dns view ! Configure DNS security no ip domain-lookup ; Don't lookup unknown names ip domain-name company.local ip host www 192.168.1.50 ip host mail 192.168.1.60

👤 Individual Activity: Configure Multi-Subnet DNS

Scenario

Your company has 3 subnets and needs a DNS infrastructure:

  • • HR Subnet (192.168.1.0/24) - DNS Server: 192.168.1.10
  • • IT Subnet (192.168.2.0/24) - DNS Server: 192.168.2.10
  • • Finance Subnet (192.168.3.0/24) - Uses 192.168.1.10

Tasks

  1. 1. Design zone files for all subnets with these records:
    • • HR: hr-server, hr-printer, hr-workstation
    • • IT: it-support, it-server, it-workstation
    • • Finance: finance-server, finance-workstation
  2. 2. Configure DNS servers for primary and secondary
  3. 3. Create forward and reverse DNS zones
  4. 4. Test DNS resolution from each subnet
  5. 5. Document DNS record mapping

Solution: Multi-Subnet DNS Configuration

; === HR SUBNET - Primary Zone === ; File: /etc/bind/zones/db.hr.local $TTL 86400 @ IN SOA ns1.hr.local. admin.hr.local. ( 2024010101 ; Serial 3600 1800 604800 86400) @ IN NS ns1.hr.local. ns1 IN A 192.168.1.10 hr-server IN A 192.168.1.50 hr-printer IN A 192.168.1.60 hr-workstation IN A 192.168.1.100 ; === IT SUBNET - Primary Zone === ; File: /etc/bind/zones/db.it.local $TTL 86400 @ IN SOA ns1.it.local. admin.it.local. ( 2024010102 ; Serial 3600 1800 604800 86400) @ IN NS ns1.it.local. ns1 IN A 192.168.2.10 it-support IN A 192.168.2.20 it-server IN A 192.168.2.50 it-workstation IN A 192.168.2.100 ; === FINANCE SUBNET - Zone === ; File: /etc/bind/zones/db.finance.local $TTL 86400 @ IN SOA ns1.hr.local. admin.finance.local. ( 2024010103 ; Serial 3600 1800 604800 86400) @ IN NS ns1.hr.local. finance-server IN A 192.168.3.50 finance-workstation IN A 192.168.3.100 ; === NAMED.CONF CONFIGURATION === zone "hr.local" { type master; file "/etc/bind/zones/db.hr.local"; allow-transfer { 192.168.2.10; 192.168.3.10; }; }; zone "it.local" { type master; file "/etc/bind/zones/db.it.local"; allow-transfer { 192.168.1.10; 192.168.3.10; }; }; zone "finance.local" { type master; file "/etc/bind/zones/db.finance.local"; allow-transfer { 192.168.1.10; 192.168.2.10; }; }; ; === VERIFICATION COMMANDS === # From HR Subnet (192.168.1.x): nslookup hr-server.hr.local 192.168.1.10 nslookup it-support.it.local 192.168.1.10 nslookup finance-server.finance.local 192.168.1.10 # From IT Subnet (192.168.2.x): nslookup it-workstation.it.local 192.168.2.10 nslookup hr-printer.hr.local 192.168.2.10 # From Finance Subnet (192.168.3.x): nslookup finance-workstation.finance.local 192.168.1.10

Key Points: Each subnet has primary DNS server with zone authority. Secondary servers in other subnets replicate data. Finance uses HR's DNS for cost efficiency. All zones configured for cross-subnet resolution.

👥 Group Activity: Enterprise DNS Migration

Scenario

Your enterprise is migrating from on-premise DNS (old.internal) to cloud-based DNS (cloud.example.com). You must ensure zero downtime for the 5000+ employees.

Deliverables (5-6 people per group)

  1. 1. DNS Migration Plan (2 people)
    • • Timeline: Stage 1 (pilot), Stage 2 (gradual), Stage 3 (full migration)
    • • Risk assessment and rollback procedures
    • • TTL reduction strategy for smooth migration
  2. 2. DNS Record Inventory & Mapping (2 people)
    • • Export all current DNS records from old server
    • • Map to new cloud DNS format
    • • Validate 100% record accuracy
  3. 3. DHCP-DNS Integration (1 person)
    • • Configure DHCP servers to point to new DNS
    • • Set up dynamic DNS (DDNS) updates
  4. 4. Testing & Validation (1-2 people)
    • • Create test scenarios for each record type
    • • Test failover scenarios
    • • Performance benchmarking (query response time)
  5. 5. Documentation & Runbook (1 person)
    • • Step-by-step migration runbook
    • • Troubleshooting guide
    • • Post-migration validation checklist

Group Activity Solution Framework

=== PHASE 1: PRE-MIGRATION (Week 1) === 1. Reduce TTL on all records from 3600 to 300 seconds 2. Set up cloud DNS with test zone 3. Run parallel DNS servers for 1 week === PHASE 2: PILOT MIGRATION (Week 2) === 1. Select 100 test users (1 dept) 2. Configure their DHCP to use new DNS: 52.x.x.x 3. Run network tests from pilot group 4. Monitor: response time, failures, resolution errors 5. Collect feedback from pilot users === PHASE 3: GRADUAL MIGRATION (Week 3-4) === Monday: 25% of users (1250) → cloud DNS Wednesday: 50% of users (2500) → cloud DNS Friday: 75% of users (3750) → cloud DNS If issues: Reduce TTL, revert DHCP settings === PHASE 4: FULL MIGRATION (Week 5) === Final 25% (1250) + admin/critical systems Decommission old DNS server after 2 weeks verification === DNS RECORD VALIDATION SCRIPT === #!/bin/bash echo "Testing DNS Migration..." # List of critical records to test RECORDS=( "mail.example.com" "intranet.example.com" "vpn.example.com" "file-server.example.com" "printer.example.com" ) for record in "${RECORDS[@]}"; do echo "Testing: $record" OLD_DNS=$(nslookup $record 192.168.1.10 | grep Address) NEW_DNS=$(nslookup $record 52.x.x.x | grep Address) if [ "$OLD_DNS" = "$NEW_DNS" ]; then echo "✓ PASS - Both IPs match" else echo "✗ FAIL - IP mismatch!" echo "Old DNS: $OLD_DNS" echo "New DNS: $NEW_DNS" fi done === ROLLBACK PROCEDURE === If issues occur during migration: 1. Immediately notify all team leads 2. DHCP servers revert to old DNS: 192.168.1.10 3. Wait 10 minutes for DNS caching to clear 4. Verify users can resolve names with old DNS 5. Root cause analysis before resuming

Success Criteria: Zero outages, 100% record migration, <50ms query response time, all user testing passing, complete documentation, and approved rollback plan.
