Network Reliability Concepts

Network reliability means: "When I need the network, it's there. When it fails, I know why and can fix it fast."

⏱️ Uptime

The percentage of time the network is working. Target: 99.9% (acceptable) to 99.99% (excellent, called "4 nines").

Example: 99.9% = only 43 min down per month

⚡ MTBF & MTTR

MTBF = Mean Time Between Failures (how long before it breaks). MTTR = Mean Time To Repair (how fast you fix it).

Higher MTBF + Lower MTTR = Better reliability

Key Reliability Strategies

🔄

Redundancy

Have backup equipment ready. If Router A fails, Router B takes over automatically. Example: dual ISPs, redundant switches, failover servers.

PhilHealth fix: Add a second internet connection + backup router

🛡️

Fault Tolerance

The system keeps running even when parts fail. RAID storage, link aggregation, clustering. One failure ≠ total system down.

PhilHealth fix: Use RAID 1 (mirroring) for database server

📋

Maintenance Planning

Preventive maintenance (scheduled updates) beats emergency repairs. Test backups monthly. Monitor proactively.

PhilHealth fix: Monthly device health checks + quarterly DR drills

📊

Monitoring & Alerting

Real-time systems watch network health. Alert staff before problems explode. Know CPU usage, bandwidth, error rates.

PhilHealth fix: Use SNMP monitoring to alert on high link utilization

📚

SLA & Recovery Plans

Service Level Agreement defines "acceptable downtime." Disaster Recovery (DR) plan explains exact steps to restore critical services.

PhilHealth fix: Define RTO (Recovery Time Objective) and RPO (Recovery Point Objective)

🧪

Testing & Validation

Regularly test: failover, restore from backups, disaster recovery procedures. Find problems in drills, not real emergencies.

PhilHealth fix: Quarterly disaster recovery simulation

Network Documentation Types

Good documentation is like a recipe book for your network. When you're gone, anyone can follow it. When disasters happen, you have the playbook.

📐

1. Physical Network Diagram

What: Visual map showing actual devices: routers, switches, servers, PCs, printers, connections.

Includes: Device names, locations (which office), physical connections, cable types, power sources.

📊 PhilHealth use: Instant location if a router dies — "It's on the 3rd floor in Comms Room"

🌐

2. Logical Network Diagram

What: Shows how data flows: IP addresses, subnets, VLAN assignments, routing paths.

Includes: IP ranges per subnet, device IPs, firewall rules, DMZ, VPN connections.

📊 PhilHealth use: Troubleshooting connectivity — "Why can't office B reach the database server?"

📋

3. Device Inventory & Configuration

What: Detailed list of every device: model, serial number, OS version, purchase date, warranty, config details.

Includes: MAC addresses, installed software, current configs, backup locations.

📊 PhilHealth use: "The backup router needs warranty support — looking it up instantly"

🧰

4. Troubleshooting Runbooks

What: Step-by-step guides for common issues: "Network down," "Can't reach server," "Slow internet."

Includes: Tests to run, expected results, resolution steps, escalation procedures.

📊 PhilHealth use: New admin can fix 80% of problems without calling you at 2 AM

🆘

5. Disaster Recovery Plan (DRP)

What: The "recover from apocalypse" playbook. Defines Recovery Time Objective (RTO) and Recovery Point Objective (RPO).

Includes: Contact list, backup locations, failover procedures, data restore steps, testing schedule.

📊 PhilHealth use: Earthquake happens, data center flooded — follow DRP, critical services back in 4 hours

📊

6. Performance & Monitoring Baseline

What: "Normal" values for CPU, memory, bandwidth, latency, packet loss. Alerts trigger when these deviate.

Includes: Monitored metrics, alert thresholds, responsible parties, trending data.

📊 PhilHealth use: Alert fires — "CPU on main switch = 95%, someone misconfigured?" vs normal 20%

🧪 Packet Tracer Lab: PhilHealth Network & Monitoring

Build a realistic multi-office network with monitoring to measure reliability.

📐 Network Topology to Build

PHILHEALTH REGIONAL HUB ISP Connection (Internet) | [Main Router] / | \ Office1 Office2 Database Switch Switch Server /|\ /|\ | PCs PCs Backup Srv Subnets: Main Office: 10.0.1.0/24 Remote Office: 10.0.2.0/24 Database Site: 10.0.3.0/24 WAN Links: 172.16.0.0/16

Demonstrates redundancy, monitoring, and failover concepts

Step-by-Step Instructions (Complete in 45 min)

Part 1: Network Topology Setup (15 min)

1

Create the network backbone

Add 1× Cisco 2821 (Main Router), 2× Cisco 1841 (Remote & DB), 3× Cisco 2960 Switches

2

Connect routers via WAN links

Serial connections: Main S0/0→Remote S0/0, Main S0/1→DB S0/0 (clock rate 64000)

3

Connect routers to switches (LAN)

Each router Fa0/0 or Fa0/1 connects to switch Fa0/1 (copper straight-through)

4

Add end devices (6 total)

Office1: 2 PCs | Office2: 2 PCs | DB Site: 1 Server + 1 Backup → connect to switches Fa0/2, Fa0/3, etc.

Part 2: IP Configuration & Routing (15 min)

5

Configure Main Router interfaces

enable → configure terminal

interface fa0/0 → ip address 10.0.1.1 255.255.255.0 → no shutdown

interface s0/0 → ip address 172.16.1.1 255.255.255.0 → clock rate 64000 → no shutdown

interface s0/1 → ip address 172.16.2.1 255.255.255.0 → clock rate 64000 → no shutdown

6

Configure Remote & DB routers similarly

Remote: Fa0/0=10.0.2.1, S0/0=172.16.1.2 | DB: Fa0/0=10.0.3.1, S0/0=172.16.2.2

7

Enable RIP v2 routing on all routers

router rip → version 2 → network 10.0.0.0 → network 172.16.0.0

8

Assign IPs to end devices

Main-PC1: 10.0.1.10 | Main-PC2: 10.0.1.20 | Remote-PC1: 10.0.2.30 | Remote-PC2: 10.0.2.40 | Server: 10.0.3.50 | Backup: 10.0.3.60 (all gateways = router on that segment)

Part 3: Monitoring & Reliability (10 min)

9

Enable SNMP monitoring on main router

snmp-server community PhilHealth RO

snmp-server location "HQ-3rdFloor"

snmp-server contact "NetAdmin-555-1234"

10

Test failover: Disable one WAN link & verify rerouting

Shutdown Main S0/0 → wait 30sec → ping from Office1 to Office2 (should still work via alternate path)

Part 4: Validation & Save (5 min)

11

Full connectivity test

Main-PC1 → ping 10.0.2.30, 10.0.3.50 (both should succeed) | Check show ip route on routers

12

Save file as: PhilHealth-Reliable-Network.pkt

File → Save As

🧪 Packet Tracer Lab: Securing BrewNet Café

Follow these step-by-step instructions in Cisco Packet Tracer. This lab simulates securing the BrewNet Café network.

📐 Network Topology to Build

☁️ INTERNET | [Router0] 192.168.1.1 / \ [Switch0] [Switch1] STAFF VLAN GUEST VLAN VLAN 10 VLAN 20 / \ \ [PC-Manager] [PC-Cashier] [Laptop-Guest] .10 .20 .100

All devices on 192.168.1.0/24 subnet

Step-by-Step Instructions

Part 1: Build the Topology (10 min)

1

Open Packet Tracer → New Project

File → New or Ctrl+N

2

Add devices from the bottom panel

• Network Devices → Routers → 1841 (drag to workspace)

• Network Devices → Switches → 2960 × 2

• End Devices → PC × 2, Laptop × 1

3

Connect with cables

• Router Fa0/0 → Switch0 Fa0/1 (Copper Straight-Through)

• Router Fa0/1 → Switch1 Fa0/1 (Copper Straight-Through)

• Switch0 Fa0/2 → PC-Manager (Copper Straight-Through)

• Switch0 Fa0/3 → PC-Cashier (Copper Straight-Through)

• Switch1 Fa0/2 → Laptop-Guest (Copper Straight-Through)

4

Rename devices

Click each device → Config tab → Display Name. Use: Router0, Switch-Staff, Switch-Guest, PC-Manager, PC-Cashier, Laptop-Guest

Part 2: Configure IP Addresses (10 min)

5

Configure the Router interfaces

Click Router0 → CLI tab → Type these commands:

enable

configure terminal

interface fa0/0

ip address 192.168.1.1 255.255.255.128

no shutdown

exit

interface fa0/1

ip address 192.168.1.129 255.255.255.128

no shutdown

exit

6

Configure PC-Manager

Click PC-Manager → Desktop tab → IP Configuration

IP: 192.168.1.10

Subnet: 255.255.255.128

Gateway: 192.168.1.1

7

Configure PC-Cashier

IP: 192.168.1.20

Subnet: 255.255.255.128

Gateway: 192.168.1.1

8

Configure Laptop-Guest

IP: 192.168.1.200

Subnet: 255.255.255.128

Gateway: 192.168.1.129

Part 3: Apply Security Controls (15 min)

9

Set a strong router password

On Router0 CLI:

enable

configure terminal

enable secret Br3wN3t$ecure!

line console 0

password C0ns0le@2024

login

exit

line vty 0 4

password R3m0te#Acc3ss

login

exit

service password-encryption

💡 "service password-encryption" encrypts all plaintext passwords in the config file

10

Create an Access Control List (ACL)

Block guest network from accessing staff network:

access-list 100 deny ip 192.168.1.128 0.0.0.127 192.168.1.0 0.0.0.127

access-list 100 permit ip any any

interface fa0/1

ip access-group 100 in

exit

💡 This means: "Anything from guest network trying to reach staff network → DENIED"

11

Configure a login banner

banner motd #WARNING: Unauthorized access is prohibited!#

💡 Legal protection — warns unauthorized users they're being monitored

12

Save your configuration

end

copy running-config startup-config

Part 4: Test & Verify (5 min)

13

Test: Staff can ping each other

PC-Manager → Desktop → Command Prompt

ping 192.168.1.20

✅ Expected: Reply from 192.168.1.20

14

Test: Guest CANNOT ping staff

Laptop-Guest → Desktop → Command Prompt

ping 192.168.1.10

❌ Expected: Request timed out (BLOCKED by ACL!)

15

Verify password protection

Close and reopen Router0 CLI. You should be prompted for a password.

✅ Expected: "User Access Verification" prompt + banner message

📊 Case Analysis: The BrewNet Breach

Read the case study below and answer the analysis questions. Submit as a written document.

Groups of 3-4 30 minutes Written Report

📖 The Incident Report

On March 15, BrewNet Café's manager arrived to find the POS system displaying a ransomware message demanding ₱50,000 in Bitcoin. Here's what the investigation revealed:

Finding 1: Weak Credentials

The router admin panel was accessible at 192.168.1.1 with username "admin" and password "admin". It had never been changed since installation 2 years ago.

Finding 2: Open Wi-Fi

The café's Wi-Fi had no password. Both customers and staff devices connected to the same network. There was no separation between guest and business traffic.

Finding 3: Phishing Email

A cashier received an email appearing to be from "Google Security" asking them to verify their account. They clicked the link on the POS computer and entered their password. Logs show the attacker used these credentials to access the router remotely.

Finding 4: No Backups

The POS database had not been backed up in over 6 months. All recent sales data, inventory records, and customer information were encrypted by the ransomware.

Finding 5: Outdated Firmware

The router was running firmware from 2021 with 3 known critical vulnerabilities. The POS software hadn't been updated in 8 months.

💰 Total Damage

₱50,000 ransom (unpaid) + ₱60,000 lost revenue (2 days closed) + ₱40,000 IT recovery costs = ₱150,000 total loss

❓ Analysis Questions (Answer all 5)

Question 1 — Identify (10 pts)

List ALL vulnerabilities present in BrewNet's network before the attack. For each vulnerability, identify which security principle it violates (Confidentiality, Integrity, or Availability from the CIA Triad).

Question 2 — Trace the Attack (10 pts)

Write a step-by-step timeline of how you think the attacker compromised BrewNet's network, from initial entry to ransomware deployment. Use the findings as evidence.

Question 3 — Prevent (10 pts)

For EACH vulnerability you identified in Q1, recommend a specific security control that would have prevented or mitigated the attack. Explain why each control works.

Question 4 — Prioritize (5 pts)

If BrewNet could only implement THREE security controls due to budget constraints, which three would you recommend and why? Rank them by importance.

Question 5 — Reflect (5 pts)

Should BrewNet pay the ransom? Defend your answer with at least 2 reasons. What should they do instead?
